Context

Planner Task 1: design the technical architecture for Stage 5 (the frontend), covering the two CES-approved backend gap-fills plus the full React application architecture, routing, typed API client, auth/session strategy, rate-limit-safe request sequencing, and production Nginx/Docker wiring. This design is grounded in the actual controllers/DTOs/entities read directly from services/*/src (auth, mfa, guest, room, booking, admin) and the real nginx/nginx.conf / nginx/nginx.prod.conf / docker-compose*.yml, not the original CLAUDE_CODE_PROMPT.md spec, which has drifted in several places.

Key facts discovered that shape this design

  • All 6 services share one MySQL database (liberta_hotel) — services duplicate read-only TypeORM entities for tables they do not own (e.g. booking-service has its own Room, RoomType, Guest entities for joins). This is the established pattern the two new endpoints must follow.
  • No CORS is enabled on any service (app.enableCors() is never called). The frontend must be served same-origin with /api/* (through Nginx) — this is already how dev and prod are wired, and it removes any need for CORS/cookie cross-site config.
  • Tokens travel as plain JSON (TokenResponseDto { accessToken, refreshToken, expiresIn }), never as Set-Cookie. This constrains the session-storage decision — httpOnly cookies are not an option without a backend change, out of scope here.
  • room-service public GET /rooms / GET /rooms/:id return raw TypeORM entities, not response DTOs, and load no relations — room.roomTypeId is present but room.roomType (the joined object) is not. The frontend must independently fetch /room-types and join client-side. This directly contradicts an assumption the original spec endpoint list would encourage.
  • BookingResponseDto never carries slipImagePath — only hasSlip: boolean. The slip is only reachable via GET /bookings/:id/slip, an authenticated binary stream.
  • general_limit (120r/min) is configured with zero burst on every location except the four sensitive-endpoint exact matches (= /api/auth/login, = /api/guests/register, = /api/bookings/draft, = /api/bookings/lookup, each burst=3 nodelay). Zero burst means nginx leaky bucket rejects (503) any second request arriving inside the same ~500ms slot — this is the direct cause of the Stage 4 503s and drives the dashboard-sequencing design.
  • Employee roleId seed values: 1 = Staff, 2 = Admin. JwtPayload { sub, username, roleId, roleName } is duplicated verbatim across every service jwt.strategy.ts.

Decisions

Decision 1 — New endpoint GET /rooms/:id/images lives in room-service

Choice: Add to room-image.controller.ts in room-service, alongside the existing POST /rooms/:id/images upload endpoint. Public, no auth (matches GET /rooms, GET /rooms/:id, GET /room-types — all public reads).

Alternatives considered: Expose from admin-service (rejected — admin-service is read-only dashboard aggregation only, per its DB grants which do not even include RoomImage). Fold into GET /rooms/:id as a nested array (rejected — RoomController and RoomImageController are already split into separate controllers/modules; room.service.ts currently has zero knowledge of the RoomImage entity).

Rationale: room-image.service.ts already injects Repository<RoomImage> and Repository<Room> (for the 404 check) — a findAllForRoom method is a one-line addition to a module that already owns this table writes.

Trade-offs: None significant — pure additive, non-breaking read endpoint.

Decision 2 — New endpoint GET /bookings/available-room lives in booking-service, not room-service

Choice: Add to booking.controller.ts in booking-service. Public, no auth (guests have no JWT at all — CreateDraftBookingDto takes a raw guestId, established in Stage 3, not a bearer token).

Alternatives considered:

  1. Put it in room-service, since "finding a room" sounds like a room-service concern.
  2. Have room-service call a new internal endpoint on booking-service (mirroring the InternalKeyGuard-protected auth.internal.controller.ts pattern).

Rationale for rejecting both: The overlap-conflict query (status IN (Draft, Reserved, CheckedIn) plus date-range overlap plus stale-Draft handling) is booking-service authoritative logic, already implemented once in booking.service.ts#createDraft. room-service has no Booking entity at all. booking-service, by contrast, already imports read-only Room and RoomType entities for exactly this kind of cross-table join — no new entity, no new service-to-service call, no new internal auth surface.

Trade-offs: booking-service public surface grows slightly; "room availability" now spans two services depending on the question asked. Judged acceptable since it mirrors DB ownership, not an arbitrary API split.

Open question for CES Should this endpoint additionally exclude rooms with Room.status IN ('Maintenance','OutOfService')? The existing createDraft write-path does not check Room.status today (only Booking overlap) — an existing Stage 3 decision this design does not change. Defaulted to also excluding Maintenance/OutOfService rooms in this new read-only resolver only (does not gate createDraft any more strictly than before). Proceeding with this default so the implementer is not blocked; reviewer/CES should confirm.

Decision 3 — Token storage: in-memory access token plus sessionStorage refresh token

Choice: Access token lives only in a React context/module-level variable (never persisted). Refresh token is written to sessionStorage under liberta_refresh_token.

Alternatives considered: (a) both tokens in localStorage (simplest, most common in tutorials); (b) both in-memory only, no persistence (most secure, but loses session on every refresh — bad UX for a staff dashboard used all shift); (c) httpOnly cookies (best practice, but requires backend changes — auth/mfa-service return tokens as plain JSON body, out of scope for a frontend-only stage).

Rationale: sessionStorage is tab-scoped and cleared on tab/browser close — no long-lived disk artifact like localStorage. Keeping the access token purely in memory means a successful XSS exfiltration of storage only yields the refresh token, which still requires an active, loggable, revocable /auth/refresh call to become useful.

Trade-offs: Page refresh requires a silent POST /auth/refresh round-trip before rendering protected routes. Closing the tab logs the user out (arguably a feature for a shared front-desk terminal). Security-relevant — flagged for the same security-auditor pass every other stage auth-adjacent decision received.

Decision 4 — mfaRequired / mfaEnrollmentRequired resolved by one shared MFA route

Choice: /admin/mfa is a single route/component that receives { tempToken, mfaRequired, mfaEnrollmentRequired } via router state and renders one of two sub-views based on mfaEnrollmentRequired.

Rationale: Both branches converge on POST /mfa/verify { tempToken, totpCode } — splitting into two routes would duplicate the verify form and the backup-code fallback. mfaRequired: false has no reachable code path under the current contract (login never returns a JWT pair directly); not building dead code for it, just documenting the gap.

Trade-offs: None.

Decision 5 — axios plus one relative-path client, not per-service base URLs

Choice: One axios instance, baseURL: '/api', matching how Nginx already strips /api/<service-path> before proxying.

Alternatives considered: fetch directly (rejected — interceptors would need hand-rolling per call site); per-service base URLs like VITE_AUTH_URL, VITE_BOOKING_URL (rejected — no CORS/same-origin already, and per-service URLs risk bypassing Nginx rate limiting by hitting a service port directly).

Decision 6 — TanStack Query for server-state, not bespoke useEffect/useState

Choice: @tanstack/react-query for all read (GET) traffic: caching, staleTime, dedup, controlled retry.

Alternatives considered: Plain useEffect/useState per page (rejected — every page would hand-roll cache/loading/error logic and, critically, hand-roll not refetching on every focus/remount — exactly the accidental burst that caused the Stage 4 503s); SWR (equally valid, TanStack Query more widely documented for this exact pattern).

Rationale: general_limit zero-burst configuration makes "do not refetch things you do not have to" a correctness requirement, not an optimization.

Decision 7 — Admin dashboard 4 calls sequenced with an enforced minimum gap, never Promise.all

Full detail in Data Flow #3. Summary: general_limit = 120r/m with no burst= parameter → nginx treats this as burst=0: only one request per 500ms slot is admitted, everything else in that window is rejected (503) with zero queuing. Promise.all across 4 endpoints guarantees at least 3 of 4 fail. Fix must be a client-side minimum-gap enforcer, not retries alone.

Decision 8 — Production frontend ships as its own Nginx-serving container

Choice: frontend/Dockerfile multi-stage: stage 1 (node:20-alpine) npm ci && npm run build; stage 2 (nginx:1.27-alpine) copies dist/ into /usr/share/nginx/html, with a small frontend/nginx.frontend.conf doing try_files $uri /index.html; SPA fallback on port 80 internally. The reverse-proxy location / becomes a plain proxy_pass http://frontend:80; — no try_files at that layer.

Alternatives considered: Shared named volume plus root/try_files directly in the reverse-proxy Nginx, populated by a one-shot init container. Rejected: (a) breaks the "every service ships its own image" convention every other service follows; (b) no existing pattern for a build-then-copy init container; (c) the currently-commented-out placeholder in nginx.prod.conf (proxy_pass ...; try_files $uri /index.html; in one location block) is actually invalid nginx — this design replaces it with a correct two-layer split.

Trade-offs: One extra proxy hop for the frontend path — negligible at this scale, and keeps the frontend independently buildable/deployable/rollback-able like the other 6 services.

Database Design

No new tables. Both new endpoints read from existing tables (Room, RoomType, Booking, RoomImage) already owned by room-service and booking-service respectively. No schema migration needed for Stage 5.

Query added to booking-service (read-only)

-- Conceptual shape of booking.service.ts#findAvailableRoom
-- No SELECT ... FOR UPDATE here -- this is a resolver, not the transactional
-- gate. createDraft existing row-locking remains the single source of
-- truth that actually prevents double-booking.
SELECT r.room_id, r.room_number, r.floor, r.room_type_id
FROM Room r
WHERE r.room_type_id = :roomTypeId
  AND r.status = 'Available'
  AND NOT EXISTS (
    SELECT 1 FROM Booking b
    WHERE b.room_id = r.room_id
      AND b.status IN ('Draft', 'Reserved', 'CheckedIn')
      -- mirrors createDraft stale-Draft self-heal: an expired-lock Draft
      -- must not block a new resolution, even though this read-only path
      -- does not itself flip it to Expired (that still only happens inside
      -- createDraft transaction or the expiry cron)
      AND NOT (b.status = 'Draft' AND b.lock_expires_at < NOW())
      AND b.check_in  < :checkOut
      AND b.check_out > :checkIn
  )
ORDER BY r.room_id ASC
LIMIT 1;

Indexes: No new indexes required — reuses the same Booking(room_id, status, check_in, check_out) access pattern createDraft existing SELECT ... FOR UPDATE already relies on. If EXPLAIN shows the correlated subquery scanning without an index during implementation, add a composite index on Booking(room_id, status) — an implementer/tester-time verification, not a new requirement introduced here.

API Contracts

NEWPublic GET /rooms/:id/images (room-service)

Auth: None.

Path param: id — ParseIntPipe, must reference an existing Room.

Response DTO:

// room-service/src/room-image/dto/room-image-response.dto.ts
export class RoomImageResponseDto {
  @ApiProperty() imageId: number;
  @ApiProperty() roomId: number;
  @ApiProperty() imagePath: string;       // e.g. "/uploads/rooms/<uuid>.jpg" -- served
                                           // statically by Nginx existing
                                           // location /uploads/rooms/ block, unchanged.
  @ApiProperty({ nullable: true }) caption: string | null;
  @ApiProperty() isPrimary: boolean;
  @ApiProperty() displayOrder: number;
  @ApiProperty() uploadedAt: Date;
}
StatusMeaning
200 OKRoomImageResponseDto[], ordered by displayOrder ASC, isPrimary DESC; [] if none.
404 Not FoundRoom does not exist (reuses the same NotFoundException the existing upload endpoint throws).

NEWPublic GET /bookings/available-room (booking-service)

Auth: None (matches POST /bookings/draft, POST /bookings/lookup).

Request DTO (query params):

// booking-service/src/booking/dto/find-available-room.dto.ts
export class FindAvailableRoomDto {
  @ApiProperty({ example: 1 })
  @Type(() => Number) @IsInt()
  roomTypeId: number;

  @ApiProperty({ example: '2026-07-10' })
  @IsDateString()
  checkIn: string;

  @ApiProperty({ example: '2026-07-13' })
  @IsDateString()
  checkOut: string;

  @ApiProperty({ required: false, example: 2 })
  @IsOptional() @Type(() => Number) @IsInt() @Min(1)
  numGuests?: number;
}

Response DTO:

export class AvailableRoomResponseDto {
  @ApiProperty() roomId: number;
  @ApiProperty() roomNumber: string;
  @ApiProperty() roomTypeId: number;
  @ApiProperty() typeName: string;
  @ApiProperty() pricePerNight: number;
  @ApiProperty() capacity: number;
  @ApiProperty() nights: number;
  @ApiProperty() totalPrice: number;       // pricePerNight * nights, precomputed
                                            // so the confirmation screen can
                                            // sanity-compare against
                                            // CreateDraftResponseDto.totalPrice.
}
StatusMeaning
200 OKAvailableRoomResponseDto for the lowest-roomId match.
400 Bad RequestcheckOut <= checkIn, or numGuests exceeds the room type capacity.
404 Not FoundNo Available-status room of that type is free for the range — message: "No available room of this type for the given dates". Treated by the UI as fully booked, not an error state.

Nginx routing — no config change needed: /api/bookings/available-room does not match either exact-match location (= /api/bookings/draft, = /api/bookings/lookup), so it falls through to the prefix location /api/bookings/ block — automatically under 120r/min general_limit, not the 8r/min sensitive tier. This is the entire point of Decision 2 and the reason CES rejected client-side retrying against POST /bookings/draft.
